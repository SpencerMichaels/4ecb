# M5.7 invited-beta deployment status

Working checklist for hosting 4ecb for the product owner's D&D group. Operator
instructions live in [`public-deployment.md`](public-deployment.md) ("Published
image", "Small-group deployment with Compose"); the homelab side (DMZ VM,
Caddy, invite gate, image follow job, pack copy) is documented in the homenet
repo's `apps/4ecb/README.md`. This file tracks what has been verified.

Last updated: 2026-10-31.

## Done

- **Container.** `compose.yaml` runs the hardened production image (read-only
  root, bounded `/tmp`, loopback-only port via `FOURECB_PORT`, image tag via
  `FOURECB_TAG`). The image serves `/private-packs/` from a read-only mount.
- **Pack advertisement.** `pnpm content-tool advertise <pack.4ecp>` validates a
  pack, copies it to `deploy/private-packs/<packId>-<digest prefix>.4ecp`, and
  writes `deploy/runtime-config.json` (ignored by git and the Docker build
  context). Content updates go to the homelab with `scripts/publish-content.sh`.
- **Local container check (2026-10-16, port 18080).** `/healthz` returns `ok`;
  the runtime config advertises the pack; it downloads in full; a missing pack
  returns 404; security headers are present; Docker reports it healthy.
- **Release pipeline (2026-10-18/19).** CI publishes `ghcr.io/spencermichaels/4ecb`
  (`main`, `sha-<commit>`) after the public checks pass; `scripts/deploy.sh`
  releases in one step; the homelab's follow job re-pins the digest and deploys
  within about 15–25 minutes. The app shows its build commit and an update icon.
- **Real host.** Live at `https://4ecb.spencermichaels.net` on the DMZ VM behind
  Caddy (HTTPS, `/healthz` through the proxy).
- **Access control.** Caddy admits only browsers holding the invite cookie, set
  by the invite link `/enter/<secret>`; everything else, `/private-packs/`
  included, gets 403 (only the PWA manifest and icon are exempt). Gate tested
  against Caddy 2.11.7 on 2026-10-18 (no/wrong/padded/lookalike cookie → 403).
- **Beta rehearsal, owner-verified on the real origin (2026-10-31):**
  1. The invite link lets a clean browser in; without it the site is refused.
  2. Onboarding finds and installs the advertised pack.
  3. Character workflow: import, creation, builder edits, sheet and print
     preview.
  4. Image update: a new release arrives, the update icon appears, and
     characters survive the update.

## Pending

1. **CSP console check.** Open the browser console on the real origin while
   using the builder, sheet and print preview; confirm no
   Content-Security-Policy errors (production CSP is stricter than the dev
   server's). The site behaves like localhost, so none are expected.
2. **Offline reload.** Install the PWA, then reload with the origin
   unreachable (stop the container, or take the device offline): the app, the
   pack and existing characters still load.
3. **Backup and restore.** Export a backup, clear the site data (or use a
   second clean browser with the invite link), restore it, and confirm the
   characters come back intact.
4. **Rollback.** Follow the homenet README's immediate-rollback path (disable
   the "4ecb follow" workflow, revert the pin commit, push), confirm the older
   build opens existing browser data, then re-enable the follow job. Worth
   checking specifically: data written by the newer build (evaluation cache
   versions, storage migrations) must not break the older one.
5. **Record and close.** Note the observed results here, then close M5.7 in
   `roadmap.md` and `implementation-status.md` together with the owner's
   approval of the parity-surface cleanup (the open passes in
   `visual-review-checklist.md`).
